# Context-compatible birth: fixed comparison

Declared 2026-09-14, before experimental play. User authorized the next increment.
Branch `codex/context-owned-decisions`; no external publication authorized.

## Single intervention

Keep the previous owner development law, except that a proposed new scoring
condition is checked against its owner's immutable path before installation.
Reject only when path AND candidate is proven unsatisfiable over the referenced
declared categorical domains. No reward, action target, empirical frequency,
task label or board enters the check. All expressions refer to the same binding
and frame. This law does not generalize automatically to temporal/noisy readers.

The supplied Boolean interpreter uses AND, OR and exactly-one (not parity).
It enumerates at most256 declared assignments, at most128 expression occurrences,
and at most32,768 node/child operations. Any inconclusive or unsupported check
permits the ordinary trial. These are logical assignments, not environment
actions, training examples or imagined outcomes. Cross-coordinate environmental
constraints are deliberately unknown: ignoring them may admit impossible trials,
but cannot justify an incorrect rejection over the declared superset.

Only contradictions are cached, with at most256 entries. Keys contain owner ID,
the entire path and candidate grammar, and typed referenced schema definitions,
plus a semantics version. Changed assumptions miss the cache. Bounded FIFO
eviction forgets a memoized proof, not the separate proposal history. Old owners'
records remain as ancestry. No learned predicate mutation occurs in this study.

Every opportunity draws at most one proposal with the unchanged distribution.
Contradiction, already-seen and graph-budget rejections get no replacement draw.
At the parameter ceiling the original law makes no draw; preserve and report this.
Filtering can therefore change later opportunity counts if resource limits bind.
No semantic duplicate merge, tautology elimination, action-sensitivity filter,
changed retirement rule or cleanup of inherited conditions is included.
Possible state-only and rare unobserved structures remain eligible.

This is generic Python developmental machinery inside the organism. It is not
a graph-learned development controller or a proof of behavioral retention.
The original `owner_development.py` and all63 original learner/core files stay
unchanged. An isolated subclass with the check disabled provides the control;
tests and historical state/log reproduction audit its copied birth law.

Reuse BOTH seeds10/11's verified event640 source checkpoints from the completed
fivefold run. No prefix training is repeated. Each source forks into disabled
control and enabled compatibility arms, with identical initial learner state,
RNG states, parameters and original continuation order. The sole configured
difference is compatibility.enabled. Both use adaptive owner splitting.

Each arm receives1,280 actual actions:640 mostly B then640 mostly A, exactly the
previous fivefold schedule. Evaluate all16 development rows without learning on
disposable clones every64 actions, then reproduce each evaluation from its saved
checkpoint. Initial scores are the verified prior evaluations, not new actions.
No milestone result changes the schedule or selects a preferred endpoint.

Totals:5,120 training +1,280 scheduled evaluation +1,280 verification actions;
80 blocks and84 newly saved actor checkpoints, plus two byte-identical source
payload copies. Immutable per-action submissions and credits, block manifests,
all checkpoints and incomplete evidence are preserved. No automatic retry.

One worker, one CPU affinity, numerical libraries one thread,2GiB address-space
cap,64MiB per-file cap,1,800s CPU/wall worker deadline; independent GNU timeout

## Measurements fixed before play

- Full original control state, training records and every evaluation must
  reproduce the prior adaptive arm (excluding the new observational metadata).
- Actual proposals, check verdicts/work, rejections and accepted births by owner;
  match expression/path/episode proposal sequences where they remain paired.
- Dead-on-arrival births, later actual participation, physical nodes, immutable
  definitions, parameters, pruning, owner visits and development opportunities.
- All row gains/losses, temporary regressions, boundary B retention and final A/B
  success; matching totals alone do not establish matching behavior.
- Wall time, peak RSS and checksum/restore results. Timing is descriptive, with
  sequential arm order and recorder costs, not a replicated speed benchmark.

It is plausible that scores stay unchanged while graphs shrink: a contradictory
condition cannot participate in credit. That would support efficient growth,
not a solution to incomplete acquisition, missed useful births or forgetting.
